### 10.5 — Escribe tus historias de usuario

HU-01. Visualización de variables del motor

HU-01 — Monitoreo en tiempo real

Como jefe de mantenimiento,
quiero visualizar en un dashboard la temperatura, vibración, corriente y velocidad del motor,
para conocer su estado de operación y detectar comportamientos anormales oportunamente.

Criterios de aceptación

Dado que el motor y los sensores están funcionando y conectados, cuando se reciben nuevas lecturas, entonces el dashboard debe actualizar las cuatro variables con una latencia inferior a 2 segundos.

Dado que existen lecturas válidas, cuando el usuario consulta el dashboard, entonces cada variable debe mostrarse con su unidad de medida y una gráfica de tendencia.

Dado que un sensor deja de transmitir datos, cuando el sistema detecta la pérdida de lecturas, entonces debe indicar que la información de esa variable no está disponible, en lugar de presentarla como actual.

HU-02. Alertas locales

HU-02 — Detección de umbrales críticos

Como operario,
quiero recibir una alerta sonora y visual cuando una variable supere su umbral crítico,
para reconocer una condición anormal y actuar oportunamente.

Criterios de aceptación

Dado que los sensores funcionan correctamente, cuando una variable supera el umbral crítico configurado, entonces el buzzer y el LED deben activarse en menos de 2 segundos.

Dado que se han definido niveles de advertencia y críticos, cuando se alcanza cada nivel, entonces el sistema debe diferenciarlos visualmente.

Dado que se pierde la conexión Wi-Fi, cuando se presenta una condición crítica detectable por el dispositivo, entonces la alerta local debe continuar funcionando sin depender de Internet.

HU-03. Notificaciones remotas

HU-03 — Notificaciones de anomalías

Como jefe de mantenimiento,
quiero recibir notificaciones remotas cuando el sistema detecte una anomalía,
para conocer los posibles problemas aunque no esté cerca del motor.

Criterios de aceptación

Dado que el sistema detecta una anomalía y existe conectividad con el servicio de notificaciones, cuando se genera el evento, entonces debe enviar la notificación en menos de 10 segundos.

Dado que se genera una notificación, cuando el usuario la recibe, entonces debe incluir la identificación del motor, la variable afectada, el valor detectado y la hora del evento.

Dado que una misma anomalía persiste, cuando se producen detecciones repetidas dentro de la ventana configurada, entonces el sistema debe evitar enviar alertas idénticas repetidamente. Si el servicio de notificaciones falla, el evento debe quedar registrado para su consulta posterior.

HU-04. Clasificación de fallas mediante IA

HU-04 — Detección inteligente de anomalías

Como ingeniero de mantenimiento,
quiero que el sistema clasifique automáticamente las anomalías del motor,
para contar con información que ayude a decidir qué inspección o intervención realizar.

Criterios de aceptación

Dado un conjunto de prueba representativo y etiquetado, cuando se evalúa el modelo entrenado, entonces debe alcanzar una precisión global (accuracy) igual o superior al 88 %.

Dado que el modelo recibe datos válidos, cuando identifica una anomalía conocida por sus clases, entonces el dashboard debe mostrar la clase detectada y su nivel de confianza.

Dado que los datos recibidos están incompletos o fuera de las condiciones admitidas por el modelo, cuando se intenta realizar la inferencia, entonces el sistema debe informar que el resultado no es confiable o no está disponible, en lugar de afirmar una clasificación válida.

HU-05. Consulta del historial

HU-05 — Historial de lecturas y eventos

Como analista de mantenimiento,
quiero consultar y filtrar el historial de lecturas y anomalías,
para identificar patrones de comportamiento y apoyar las decisiones de mantenimiento.

Criterios de aceptación

Dado que existen registros almacenados, cuando el usuario selecciona un rango de fechas, entonces el sistema debe mostrar las lecturas y los eventos correspondientes al periodo.

Dado que existen registros de distintas variables y eventos, cuando el usuario aplica filtros, entonces el sistema debe permitir consultar la información por variable y tipo de evento, y exportar a CSV.

Dado que no existen registros para el filtro seleccionado o se produce un error al consultar la base de datos, cuando se solicita el historial, entonces el sistema debe mostrar un mensaje claro y no presentar datos incorrectos como si fueran resultados válidos.

HU-06. Funcionamiento sin conexión

HU-06 — Almacenamiento temporal de telemetría

Como técnico de campo,
quiero que el dispositivo almacena temporalmente las lecturas cuando se pierde la conexión y las sincronice al recuperarla,
para reducir la pérdida de información durante interrupciones de la red.

Criterios de aceptación

Dado que el dispositivo pierde la conexión, cuando continúa recibiendo lecturas de los sensores, entonces debe almacenarlas localmente durante al menos 30 minutos.

Dado que la conexión se restablece, cuando el dispositivo vuelve a comunicarse con el servidor, entonces debe sincronizar las lecturas pendientes en orden cronológico.

Dado que el almacenamiento local se llena o falla, cuando no es posible guardar una lectura, entonces el sistema debe indicar el problema y evitar informar que el dato quedó almacenado correctamente.
